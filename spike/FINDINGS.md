## 2. Primitives used, and how they composed

| Primitive (public header) | Role in the adapter |
|---|---|
| `kl_socket_provider_posix()` -> `->ops` (`keel/socket.h`) | The socket data plane. `ops->socket/connect/send/recv/close/set_nonblocking/get_so_error/bind/listen/accept/get_local_addr` called **directly**. |
| `KlSockAddr` + `kl_sockaddr_from_ipv4` / `kl_sockaddr_port` / `kl_sockaddr_set_port` (`keel/sockaddr.h`) | Build numeric targets and read the peer's ephemeral bind port. No platform `struct sockaddr` crosses the adapter. |
| `KlConnectOp` + `connect_op_detail.h` (`keel/connect_op.h`) | Embedded, terminal-exactly-once connect orchestrator. The adapter supplies `KlConnectOpHooks` and drives the on_* entry points; it now RACES a real multi-address list and survives a first-address failure. |
| `KlStream` + `stream_detail.h` (`keel/stream.h`) | Embedded raw byte transport. WRITE: `kl_stream_write_init`/`set_writer`/`write` + `kl_stream_flush` on write-readiness (backpressure). READ: `kl_stream_read_init(completion_mode=0, ...)` + `read_start` + `on_recv` + `pause`/`resume` (the TLS upgrade window). CLOSE: `close_init`/`close_begin`/`cancel` -> `on_close` confirms detachment. |
| `KlResolver` + `kl_dns_resolver_create` (`keel/resolver.h`, `keel/dns_resolver.h`) | The REAL async resolver vtable KlConnectOp calls (TEST 10), plus a synthetic multi-address resolver (TEST 3) that races an unconnectable address then the good one. |
| `KlEventCtx` (`keel/event_ctx.h`) + `keel/event.h` | The single event loop. `kl_event_ctx_init/free`, `kl_watcher_add/mod/del`, `kl_event_ctx_run`. |
| `KlTimer` (`keel/timer.h`) | The overall connect deadline via `kl_timer_add`/`kl_timer_cancel`, armed/cancelled through the connect-op deadline hooks. TEST 4 proves it ACTUALLY FIRES. |
| `KlTls` + `keel_tls_mbedtls.h` (`keel/tls.h`) | LIVE client TLS: `kl_tls_mbedtls_client_ctx_create[_from_buf]` / `kl_tls_mbedtls_create` / `set_hostname` / `handshake` / `read` / `write` / `shutdown` / `destroy`. Server side (the in-process peer): `kl_tls_mbedtls_ctx_create` from the spike cert/key. |
| `KlAllocator` (`keel/allocator.h`), `KlError` (`keel/error.h`) | A PERSISTENT `kl_allocator_default()` copy for the stream write queue + every KlTls/KlTlsCtx (they capture the allocator by pointer and deref at destroy). `KL_ERR_CONNECT`/`_TIMEOUT`/`_DNS` as failure codes. |

TLS lives ABOVE the raw stream exactly as the KlStream contract prescribes: once
`handshake` returns OK, the stream's writer routes through `tls->write` and the
read watcher pulls plaintext via `tls->read` (draining `tls->pending()` so an
edge-triggered loop never strands a decrypted record).

## 3. Reviewer item 1 - completion/IOCP is OUT OF SCOPE

**Hull ships NO native-Windows runtime.** Hull's Windows story is the
Cosmopolitan APE, which selects Keel's **poll** backend (readiness). So Hull's
shipped runtime is readiness-only across every target it runs on:

- Linux: epoll (readiness)
- macOS: kqueue (readiness)
- Windows / everywhere else (Cosmo APE): poll (readiness)

IOCP / io_uring completion backends are therefore **not in Slice 2a scope** for
Hull, and this spike makes **no** claim about them. The original spike's
"completion is API-feasible" language is withdrawn: completion was never
exercised, and a completion port would require a materially different transport
(a `completion_mode=1` READ facet with a `post_recv` arm, a `kl_stream_set_submit`
WRITE facet driven by WRITE completions, and the memory-BIO `feed_input` /
`drain_output` TLS path instead of the socket-BIO `handshake(fd)`). Unproven,
out of scope, and irrelevant to what Hull ships.

The adapter code itself is backend-agnostic (it names no backend; it uses
`KlEventCtx` + `kl_watcher_*` + `kl_event_ctx_run`). That is why the SAME source
runs unchanged on kqueue and poll here, and would run on Linux epoll and the
Cosmo APE poll build in CI.

## 4. Reviewer item 2 - write backpressure (PROVEN LIVE)

**TEST 2** forces the exact condition the reviewer described. The in-process peer
stops reading the instant it has sent the EHLO `250` reply; the client then writes
a 3 MiB payload into a socket the peer refuses to drain. The single `send`
fills the kernel send buffer and returns a **partial** count (a partial write is
backpressure just as much as an `EAGAIN`); `KlStream` queues the remainder.

The adapter's writer (`smtp_stream_write`) detects the partial/would-block and
**arms a WRITABLE watcher** (keeping READ interest). When the test lets the peer
resume reading, the writable watcher fires and calls **`kl_stream_flush`**, which
drains the queue through the writer until empty; the writer then drops WRITE
interest. The full payload arrives intact and the SMTP conversation completes.

Asserted (all pass):
- `op.write_wouldblocked` - the writer actually reported would-block/partial
  (congestion was really forced, not assumed).
- `op.flush_after_wouldblock` - a WRITABLE-driven `kl_stream_flush` actually
  drained the queue (the re-arm path executed).
- `kl_stream_write_pending(&op.stream) == 0` - the queue drained to empty.
- `op.quit_ok` - the conversation completed AFTER the drain (no stall).

Without the writable re-arm the connection would stall with bytes stranded in
the queue; the test would hang and fail. It does not.

The prior spike had NO writable watcher: any congested write would have stalled.
That gap is now closed and load-bearing.

## 5. Reviewer item 3 - TLS is LIVE (not `if (0)`)

The `if (0)` compile-only block is gone. TLS now runs against a **real mbedTLS
peer** stood up in-process on the same event loop, terminating with the spike's
own self-signed cert (`spike/tls/server.crt`, CN/SAN `spike.local`).

Four TLS tests, all live, all pass:

**(a) STARTTLS in-place upgrade (verify OK)** - plaintext greeting/EHLO, the peer
advertises `250-STARTTLS`, the client sends `STARTTLS`, the peer replies
`220 Ready to start TLS`, then the channel upgrades IN PLACE on the same fd. After
the handshake the client re-EHLOs and QUITs over the encrypted channel.

**(b) implicit TLS / SMTPS (verify OK)** - the client handshakes immediately on
connect, BEFORE any application bytes; the SMTP greeting itself arrives encrypted.

**(c) STARTTLS hostname MISMATCH -> REJECTED** - verify against the correct CA but
request hostname `wrong.example`; `tls->handshake` returns `KL_TLS_ERROR`, the
adapter fails closed (`kl_stream_cancel`), and **no** plaintext/insecure SMTP
conversation completes.

**(d) implicit TLS unknown CA -> REJECTED** - verify against an UNRELATED CA
(`spike/tls/other.crt`); the chain does not validate, handshake fails, fail
closed, no fallback.

Proven properties:

- **STARTTLS buffer boundary (no plaintext across the upgrade).** Two independent
  checks: (i) at the `220`, the client asserts its accumulated reply ends EXACTLY
  at the `220 ...\r\n` line with zero trailing bytes; (ii) while `tls_handshaking`
  the raw read side is paused, so a plaintext deliver during the handshake window
  is counted and asserted to be **0**. The peer, by construction, sends only the
  `220` line and then reads the ClientHello via mbedTLS itself (the peer does NOT
  `recv` the ClientHello into a plaintext buffer, which would steal it from
  mbedTLS - a bug caught and fixed during the spike).
- **Handshake watcher transitions.** `tls->handshake` returns `WANT_READ` /
  `WANT_WRITE`; the adapter re-arms a DEDICATED handshake watcher for exactly that
  direction via `kl_watcher_mod` and yields to the event loop. Each test records
  that at least one WANT_READ/WANT_WRITE transition was observed and re-armed
  (`want_read seen=1`), so the readiness re-arm is exercised, not bypassed by a
  synchronous complete.
- **Certificate + hostname verification succeeds** against the CA (cases a, b),
  and a **negative case is REJECTED** with no plaintext fallback (cases c, d).
- TLS read/write route through the KlStream writer/read hooks (`tls->write` in
  `smtp_stream_write`, `tls->read` in the read watcher, draining `tls->pending()`).

This mirrors `src/hull/shared/tls_client.c` for context creation and the WANT_*
loop; the difference is this spike drives the loop on the event loop (readiness
re-arm) instead of a blocking `poll`, which is what the reviewer asked to see.

One real bug the live TLS work surfaced and fixed: KlTls/KlTlsCtx capture the
`KlAllocator` **by pointer** and dereference it at destroy time, so a stack-local
`kl_allocator_default()` dangles and crashes `tls_destroy`. The spike now holds a
PERSISTENT allocator (exactly as `shared/tls_client.c` documents). This is a
useful confirmation for the production retrofit.

## 6. Reviewer item 4 - resolution race, fired deadline, cancel-during-resolve

The connect path no longer synthesizes one numeric address.

**TEST 3 - multi-address race, first fails, second wins.** The adapter hands
KlConnectOp a TWO-address list: a closed loopback port (bound then closed, so
nothing listens -> `ECONNREFUSED`) followed by the good peer. KlConnectOp starts
attempt 0; on its failure it fast-starts attempt 1, which wins. Asserted:
`attempt_fail_count >= 1` (the first address really failed) AND the conversation
completed via the winner (`quit_ok`) AND clean single detachment.

**TEST 10 - the REAL resolver.** `kl_dns_resolver_create` resolves `localhost`
via its `/etc/hosts` fast path (no network), returning `127.0.0.1`; the adapter
retargets the port to the peer and connects. This exercises the actual
`KlResolver` vtable + `KlResolveResult` multi-address contract KlConnectOp would
use, not a hand-synthesized address. (If `kl_dns_resolver_create` returns NULL
on a host without resolv.conf, the test SKIPs with a note; TEST 3 still covers
racing.)

**TEST 4 - the deadline ACTUALLY FIRES.** A real non-blocking `connect` to
TEST-NET-1 (`192.0.2.1`, RFC 5737, guaranteed non-routable) goes `EINPROGRESS`.
To make the fired-deadline path DETERMINISTIC (independent of how fast the host
delivers `ENETUNREACH`), the attempt fd is left pending with NO watcher, so its
SO_ERROR is never observed and the overall deadline is the only thing that can
terminate the op. The `kl_timer_add` deadline fires
(`co_on_deadline_fired` runs), `kl_connect_op_on_deadline` drives the op to
terminal **FAILED** with `KL_ERR_TIMEOUT`, the pending attempt is cancelled and
its fd disposed, and the op detaches cleanly. Asserted: `deadline_fired`,
`result == FAILED`, `error == KL_ERR_TIMEOUT`, single detach, no fd leak.

**TEST 5 - cancel DURING resolution.** `start_resolve` leaves the resolve in
flight (reports no addresses). The test asserts the op is in `RESOLVING`, then
calls `kl_connect_op_cancel`. The adapter's `cancel_resolve` retires the in-flight
resolve (via `kl_connect_op_on_resolve_failed`, so the machine's `resolve_inflight`
op is physically retired and detachment can proceed). Asserted: `cancel_resolve`
invoked, `result == CANCELLED`, single detach, and NO fd was ever created.

**TEST 6 - cancel DURING the connect race** (retained) complements TEST 5:
cancel while `CONNECTING` disposes the racing fd and detaches CANCELLED.

## 7. Reviewer item 5 - watcher arming no longer masks failures

The prior `smtp_stream_read_arm` treated EVERY `kl_watcher_add` non-zero return
as "already registered" and returned success. That masked real allocation/backend
failures. Fixed with EXPLICIT ownership:

- A `WatcherState { armed, mask }` per fd tracks whether a watcher is currently
  installed and its interest mask. `stream_watch_set(op, mask)` installs via
  `kl_watcher_add` the first time and `kl_watcher_mod` thereafter; it returns 0
  only on genuine success and **-1 on a real `kl_watcher_add`/`kl_watcher_mod`
  failure**.
- Every caller FAILS CLOSED on -1: the writer returns -1 (KlStream errors the
  write), `smtp_stream_read_arm` returns -1 (KlStream terminates the read op),
  and the connect-attempt path disposes the fd and reports a hard failure. None
  silently continues.
- The same explicit-ownership discipline governs the WRITABLE watcher from item 2
  and the DEDICATED TLS handshake watcher (its `kl_watcher_add` failure fails
  closed too).

A duplicate add is now impossible-by-construction (we only `add` when
`!armed`, else `mod`), so there is no "already registered" case to mistake for a
real error.

## 8. Reviewer item 6 - fd-leak evidence rests on assertions, not ASan

Descriptor-closure is proven by **explicit, deterministic assertions**, not ASan:

- Lifecycle / backpressure / race / TLS tests each assert
  `!kl_handle_valid(op.fd)` after `on_close` fires (the client fd was closed).
- The deadline and cancel tests assert `!kl_handle_valid(op.attempt_fd[...])`
  (the racing fd was disposed).
- The connect op's `on_done`/`on_detach` counters are each asserted to be exactly
  1 (no double-fire, no missed terminal).

These hold on every platform regardless of sanitizer. **ASan's role is narrower
and stated honestly: it proves no heap use-after-free / double-free / buffer
overflow in the run.** On macOS ASan has NO LeakSanitizer, so a pure heap *leak*
would be caught by Hull's Linux CI, not here. The fd-closure claim does NOT rest
on ASan; it rests on the assertions above. (The KlTls-allocator UAF in section 5
is exactly the kind of thing the ASan run guards against; with the persistent
allocator, the ASan run is clean.)

## 9. Seam dispositions (no Keel change, no facade)

On the current evidence, **no Keel seam and no Hull-side facade should be added
for a POSIX/readiness SMTP transport.** Specifically:

- **`io_status` NULL + hosted-errno fallback is the DEFINED public contract.**
  The POSIX provider leaves `ops->io_status` NULL and Keel documents the hosted
  `errno` fallback (`keel/socket.h`). The spike reads `errno` for
  would-block / `EINPROGRESS` classification, exactly as specified. This is NOT a
  gap and needs NO new provider op. (A future freestanding provider would supply
  `io_status`; that is a provider-authoring concern, already expressible through
  the existing public `KlIoStatus` type.)
- **No `KlEventCtx` socket-provider accessor is needed.** The adapter holds the
  explicitly-selected POSIX provider (`kl_socket_provider_posix()`) in its own
  struct and calls `->ops->*`. For Hull's native-fd SMTP that is complete and
  correct; there is no need to reach the ctx's internal `sockets` field or add a
  public accessor.
- **No shared transport abstraction / facade.** The adapter is throwaway spike
  code composing public primitives directly; nothing here argues for a new
  Hull-side wrapper layer. The production retrofit of `cap/smtp.c` can compose the
  same public primitives inline.

Every primitive the adapter needed (connect-op, stream, resolver, timer, event,
socket ops, TLS) is present and public. Nothing was reached for that only exists
behind a `src/` header.
