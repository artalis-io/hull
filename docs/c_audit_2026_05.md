## Critical Issues

| # | File:Line | Issue | Description |
|---|-----------|-------|-------------|
| C-1 | `src/hull/runtime/lua/mod_worker.c:106-108` | Integer overflow in capacity doubling | `new_cap *= 2` in a `while` loop can wrap to 0 on overflow, causing undersized `realloc` and heap buffer overflow |
| C-2 | `src/hull/runtime/lua/mod_gpu.c:98-100`, `src/hull/runtime/js/mod_gpu.c:92-94` | Path traversal in `gpu.load()` | User-supplied shader name concatenated into filesystem path without validation; `../../../etc/passwd` escapes `shaders/` |

### C-1: Integer overflow in bytecode writer capacity doubling

```c
// src/hull/runtime/lua/mod_worker.c:105-109
if (bw->len + sz > bw->cap) {
    size_t new_cap = bw->cap ? bw->cap * 2 : 4096;
    while (new_cap < bw->len + sz)
        new_cap *= 2;  // <-- wraps to 0 if new_cap >= SIZE_MAX/2+1
    uint8_t *nb = realloc(bw->buf, new_cap);
```

**Fix:** Add overflow guard before the doubling loop:
```c
size_t new_cap = bw->cap ? bw->cap * 2 : 4096;
while (new_cap < bw->len + sz) {
    if (new_cap > SIZE_MAX / 2) return 1;
    new_cap *= 2;
}
```

### C-2: Path traversal in gpu.load()

```c
// src/hull/runtime/lua/mod_gpu.c:97-100
snprintf(path, sizeof(path), "%s/shaders/%s.wgsl",
         lua->base.app_vfs->root_dir, name);
FILE *f = fopen(path, "r");
```

The `name` parameter comes directly from user code (`luaL_checkstring` / `JS_ToCString`) with no validation. A name like `../../etc/passwd` would construct a path outside the app directory. The kernel sandbox (unveil/seatbelt) provides defense-in-depth, but the application layer should reject traversal attempts.

**Fix:** Validate the shader name before path construction:
```c
if (!name[0] || name[0] == '/' || strstr(name, ".."))
    return luaL_error(L, "invalid shader name: %s", name);
```

### H-1: Integer overflow in migration list capacity

```c
// src/hull/migrate.c:200-202
if (ml->count >= capacity) {
    capacity *= 2;  // <-- no SIZE_MAX/2 check
    char **tmp = realloc(ml->names, (size_t)capacity * sizeof(char *));
```

The same pattern is correctly guarded in `src/hull/cap/tool.c:292` with `if (cap > SIZE_MAX / 2)`.

**Fix:**
```c
if (capacity > SIZE_MAX / (2 * sizeof(char *))) {
    migration_list_free(ml);
    closedir(dir);
    return -1;
}
capacity *= 2;
```

### H-2: Unchecked strdup for column names

```c
// src/hull/worker_db.c:271-274
for (int i = 0; i < r->ncols; i++) {
    const char *name = sqlite3_column_name(stmt, i);
    r->col_names[i] = strdup(name ? name : "?");
    // strdup can return NULL — no check
}
```

If `strdup` fails, `r->col_names[i]` is NULL. Later code passes these names to `JS_SetPropertyStr` / `lua_setfield` which will crash on NULL.

**Fix:** Check and fail early:
```c
r->col_names[i] = strdup(name ? name : "?");
if (!r->col_names[i]) {
    op->error = 1;
    snprintf(op->error_msg, sizeof(op->error_msg), "out of memory");
    sqlite3_finalize(stmt);
    return;
}
```

### H-3: memcpy with potentially NULL source pointer

```c
// src/hull/worker_db.c:145-149
const char *text = (const char *)sqlite3_column_text(stmt, col);
size_t len = (size_t)sqlite3_column_bytes(stmt, col);
out->s = malloc(len + 1);
if (out->s) {
    memcpy(out->s, text, len);  // text can be NULL
```

Per C standard, `memcpy(dst, NULL, 0)` is undefined behavior even when `len` is 0. SQLite returns NULL text/blob for NULL column values, but the type check dispatches to `SQLITE_TEXT` / `SQLITE_BLOB` before this code runs, not `SQLITE_NULL`. In practice, SQLite's type affinity means this path is rarely hit with NULL, but it's technically UB.

**Fix:** Guard the memcpy:
```c
if (out->s && text) {
    memcpy(out->s, text, len);
    out->s[len] = '\0';
} else if (out->s) {
    out->s[0] = '\0';
    out->len = 0;
}
```

### M-1: Unchecked strdup in migration status

```c
// src/hull/migrate.c:367-368
for (int i = 0; i < count; i++)
    names[i] = strdup(first[i].name + 11);  // no NULL check
```

If any `strdup` fails, `names[i]` is NULL. Later at line 408, `strcmp(names[i], ...)` will crash.

**Fix:** Check each strdup and clean up on failure.

### M-2: Large stack allocation in agent_lib

```c
// src/hull/agent_lib.c:688
char buf[65536];
size_t n = fread(buf, 1, sizeof(buf) - 1, f);
```

This is in the `hull agent errors` command path. A 64 KB stack allocation is safe on typical systems but risky in resource-constrained or deeply-nested contexts. Consider heap allocation.

### M-3: Dual path validation in Lua require

The Lua module loader at `mod_fs.c:159-296` implements custom `normalize_path()` + `strncmp` prefix checking rather than delegating to `hl_cap_fs_validate()` which uses `realpath()` for symlink-aware ancestor verification. This creates two validation implementations that could diverge.

The comment in the code notes the sandbox may block `stat()` on parent directories, which is a valid reason for string-level validation. But it means the Lua require path doesn't get symlink resolution.

## Summary

The Hull codebase demonstrates strong security discipline. The capability layer enforcement is solid — no runtime binding bypasses the `hl_cap_*` boundary for data access. SQL injection is structurally impossible. The sandbox is properly layered (application + kernel).

The findings are concentrated in two areas:
1. **Integer overflow in capacity doubling** (C-1, H-1) — missing `SIZE_MAX/2` guards that are correctly applied elsewhere in the codebase
2. **Unchecked `strdup()` returns** (H-2, M-1) — memory allocation failures propagate as NULL without error handling
3. **Path traversal in `gpu.load()`** (C-2) — user input concatenated into filesystem path without validation

All critical and high issues have straightforward fixes. The codebase is well-structured for auditing — consistent naming, clear capability boundaries, and comprehensive test coverage.
