### Recommendations

1. **Add a snprintf-accumulator helper** to be reused everywhere we incrementally build a buffer (M1 and several lower-severity sites). Something like `hl_snprintf_append(char **p, size_t *remaining, const char *fmt, ...)` that returns `-1` on truncation and updates both cursors. Replaces the brittle `req_len += snprintf(...)` idiom that recurs in `agent/request.c`, `cap/smtp.c`, and the runtime template code.
2. **Audit every `strdup` for NULL return** in the deep-copy paths that ferry data to thread-pool workers (M2/M3). These OOM-induced corruptions are the only ones the kernel sandbox cannot catch; they happen on the host thread between bind and dispatch. A short helper `static char *xstrdup_or(const char *s, int *err)` would unify the check.
3. **Treat `hl_parse_size` errors the same as `strtol` errors** at the CLI layer (L1). The mixed pattern (`-p` validates strictly, `--wasm-heap` silently falls through) is a usability bug today and a security bug the day someone removes the downstream `> 0` guard.
4. **Add unit tests for the migration system** (`hl_migrate_*` in `src/hull/migrate.c`). The audit found no `tests/hull/*` suite exercising the C-level migration API; only `e2e_migrate.sh` covers it end-to-end. Edge cases like checksum mismatch, missing migrations table, and concurrent migration attempts deserve in-process tests.
5. **Add a unit test for the sandbox layer** at least for the manifest-to-Seatbelt-profile / manifest-to-unveil-paths translation in `sandbox.c`. Today only the e2e tests exercise it, and they only run on certain hosts (OpenBSD/Linux/macOS each cover different branches). A unit test that calls the profile-build helper and asserts on the generated SBPL/unveil-path list would catch regressions on platforms CI doesn't run.
6. **Build hardening is in good shape**: `-std=c11 -Wall -Wextra -Wpedantic -Wshadow -Wformat=2 -fstack-protector-strong -D_FORTIFY_SOURCE=2 -Werror` for Hull code, `-w` only for vendored. `make debug` enables ASan+UBSan, `make msan` covers uninitialised reads.

### Notes — what was reviewed and found clean

- **Memory safety:** zero `strcpy`/`strcat`/`sprintf`/`gets`/`sscanf` uses anywhere in `src/hull/`. All `snprintf` with literal `3`/`5` are safe hex byte encoders. All `strncpy` (3 instances) are explicitly null-terminated. No VLAs; large stack buffers cap at ~8 KB (`crypto.c` `stack_buf[8192]`) which is well within the per-thread stack budget.
- **Integer overflow:** `cap/crypto.c` (lines 475, 515, 662, 698, 740, 776) explicitly guards against `SIZE_MAX/2` overflows before `msg_len + N` and `padded_len * 2`. The DB-query column allocator at `cap/db.c:257` and the prepared-statement cache at `cap/db.c:79` both check `SIZE_MAX / sizeof(HlColumn)`. `cap/tool.c:289` guards `cap * 2` realloc. `cap/wasm_stream.c:42` rejects doubling overflow.
- **Capability boundary:** Lua and JS bindings never call `sqlite3_*` directly except in three controlled places — (a) the UDF callback bridge in `runtime/{lua,js}/mod_db.c` where SQLite is the caller, (b) the worker-thread DB code in `runtime/{lua,js}/worker_db.c` that goes through `hl_worker_db_get_and_prepare()` which calls `hl_cap_db_check_namespace()` to block `_hull_*` access (`worker_db.c:113`), and (c) the agent CLI tool `agent/db.c` which is a developer-only out-of-band introspector. Stdlib bypass via call-stack inspection (`lua_is_stdlib_caller` in `mod_db.c:157`, `js_is_stdlib_caller` in `mod_db.c:159`) is intact and uses `ar.source`/`JS_GetScriptOrModuleName` to gate `_hull_*` access.
- **Path traversal:** every direct `fopen` in runtime code (`mod_gpu.c:104/109`, `mod_template.c:95/120`, `mod_fs.c:417`, `mod_tool.c:236/272/372/388`, `runtime/js/runtime.c:303/655/1031`) is either (a) preceded by `hl_cap_fs_validate` / `hl_cap_fs_*`, (b) module-loader code that already validates against `..` and absolute paths (`hl_js_validate_module_name` at `runtime/js/runtime.c:65`, `resolve_module_path` at `mod_fs.c:222`), (c) shader/template loaders that explicitly reject `..` / `/` / `\`, or (d) the `hl_tool_*` unveil-checked tool-mode FS used only during `hull build`.
- **Sandbox:** Lua removes `io`, `os`, `loadfile`, `dofile`, `load` and never loads `debug`. Only the safe libraries (`base`, `table`, `string`, `math`, `utf8`, `coroutine`) are required (`runtime/lua/runtime.c:158-170`). QuickJS removes `eval` and `Function` and never adds `std`/`os` modules (`runtime/js/runtime.c:402-413`). `JS_AddIntrinsicEval` is added because `JS_Eval` from C still needs it for module compilation, but the JS-visible globals are gone.
- **Resource management:** 38 `fopen` paired with 109 `fclose` (extra calls are error-path closes). All 9 `sqlite3_prepare_v2` sites have matching `sqlite3_finalize`, including the cache eviction path in `cap/db.c:70`. `hl_alloc_realloc` correctly handles shrink (`alloc.c:62`). `hl_worker_db_op_free` cleans up partial state (`worker_db.c:419`).

### Recommendations

1. **Sandbox safety is in good shape.** No `eval`, `Function`, `new Function`, `Proxy`, `WeakRef`, `FinalizationRegistry`, prototype mutation, or non-`hull:*` imports anywhere in the stdlib. The single `globalThis.arg` read in `verify.js` is intentional (CLI tool entry). The template engine's only code-compile path is the C bridge `_template.compile()`. Continue treating that as the only allowed `JS_Eval` site.
2. **The template engine's defenses are solid.** All identifiers are validated via `IDENT_RE`, all dot-path access uses optional-chaining on the literal `__d`, all internal maps use `Object.create(null)`, filter args are regex-validated before insertion, extends/include depth + cycle detection are in place, and JSON-stringification with `<` → `<` escaping is used for the `json` filter. The one improvement worth making is hardening `for` against non-array iterables (M-9).
3. **HL_ENABLE_DB=0 compatibility.** The following modules `import { db } from "hull:db"` at top level and will fail to load in compute-only builds: `search.js`, `middleware/idempotency.js`, `middleware/transaction.js`, `middleware/session.js`, `middleware/rbac.js`, `middleware/inbox.js`, `middleware/outbox.js`. `middleware/health.js` correctly does **not** import db at top level — it accepts the db module via `setDb()` / `opts.db`, so it works in DB-less builds. Consider documenting this list in `docs/architecture.md`.
4. **Constant-time secret comparisons are consistent.** `jwt.js`, `csrf.js`, and `idempotency.js` all use the same XOR-accumulate pattern with length-leak comments. Good practice maintained across the codebase.
5. **Address the JS-vs-Lua API-naming drift** (L-1, L-2, L-3). Each individual mismatch is minor, but together they create friction for developers switching between runtimes. A short follow-up pass to align option names (camelCase in JS, snake_case in Lua, both accepted where ambiguous) would close the gap cheaply.

### Recommendations

1. **Fix H-1 (email.lua nil deref) first** — it's the only finding that crashes a live request handler, and it's easily reachable (any DNS hiccup to Postmark/SendGrid/Resend).
2. **Close the jwt parity gap (M-1)** — `exp` semantics differing silently between runtimes is the worst kind of API inconsistency; cross-runtime apps will produce immediately-expired tokens.
3. **Audit replayable-header semantics in `idempotency.lua` (M-3)** — even if there's no concrete exploit today, replaying `Set-Cookie` from old responses is a footgun.
4. **Apply the truthiness fix (M-2) consistently** — `if opts.X ~= nil then` everywhere a numeric option might legitimately be `0` (`ttl`, `max_attempts`, `max_age`, etc.).
5. **Patch the vendored `json.lua` parser (M-7)** — Hull ships only one JSON decoder, and JSON often arrives from untrusted sources (webhooks, request bodies); O(n²) here is a DoS amplifier.
6. **DB-mode dependencies (informational):** the following Lua modules require `HL_ENABLE_DB=1` and will fail to load in compute-only builds: `middleware/session`, `middleware/idempotency`, `middleware/inbox`, `middleware/outbox`, `middleware/rbac`, `search`. Document this in the module-reference table in `CLAUDE.md`.
7. **Sandbox audit clean:** no findings under load/loadstring/dofile/loadfile, no `_G` writes, no metatable manipulation on shared objects, no `debug.*`, no `rawset` on shared tables. `tool.loadfile` is correctly scoped to tool-mode (CLI) modules only and never reachable from request handlers.
8. **SQL injection clean:** every `db.exec`/`db.query` call passes user data via `?` placeholders. Identifier-interpolation in `search.lua` is guarded by a strict regex + SQL-keyword denylist + `_hull_` prefix block. No string-concatenation SQL with user data found.
9. **Crypto clean:** all HMAC comparisons (`jwt.lua`, `middleware/csrf.lua`, `middleware/idempotency.lua`) use length-prefixed constant-time loops. Session IDs are 32-byte `crypto.random` hex; no `math.random` used for security purposes.
10. **Template engine codegen clean:** `validate_ident` rejects all dot-path parts not matching `^[%a_][%w_]*$` before they reach generated Lua source; filter string literals reject backslashes and require balanced quotes; raw text uses `lua_quote` with dynamic `[=[…]=]` levels (modulo M-6). No path for user data to be injected as Lua code. Inheritance and include depth are capped (`MAX_EXTENDS_DEPTH=8`, `MAX_INCLUDE_DEPTH=16`) and cycles are detected.
